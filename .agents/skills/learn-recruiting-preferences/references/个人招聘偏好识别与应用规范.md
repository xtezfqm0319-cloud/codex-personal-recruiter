# 个人招聘偏好识别与应用规范

本文定义如何把用户的明确反馈转成可复用、可验证、可撤销的个人招聘判断偏好。它约束的是 AI 如何理解和应用用户的判断方式，不代替公司标准、岗位画像或用户对具体候选人的正式决定。

## 1. 适用目标

偏好学习只解决三个问题：

1. 用户这次在纠正什么判断；
2. 其中是否存在未来可复用的取舍规则；
3. 经用户确认后，这条规则将在什么范围内怎样改变后续工作。

它不负责把用户每次推进或淘汰都解释成长期偏好，也不负责替用户决定某条规则是否正确。

## 2. 基本原则

- **先理解个案，再考虑泛化**：个案结论永远先于长期规则提炼。
- **明确反馈优于行为猜测**：用户原话比 AI 从结果反推的动机可靠。
- **可观察行为优于标签**：规则应落到做过什么、如何判断、承担什么结果。
- **最小适用范围**：证据不足时缩小范围，不追求一句话覆盖所有岗位。
- **先提案后生效**：未确认规则只能进入待确认区。
- **保留反例**：不能把支持案例当成无条件定律。
- **人工决定独立**：偏好影响 AI 判断方式，不自动改变已有人工正式结论。

## 3. 六层反馈分类

### 3.1 个案决定

只适用于当前候选人或当前选择，例如：

- “这个人先推进，我想通过面试再看看。”
- “这次不是能力问题，是当前没有合适的机会。”
- “A 排在 B 前面，因为这批只有一个名额。”

这类反馈应忠实更新当前事项，但默认不形成长期偏好。

### 3.2 岗位专属标准

只适用于一个正式岗位，例如：

- 某岗位当前阶段更需要从零搭建，而不是成熟体系维护；
- 某岗位必须能处理某类具体业务约束；
- 某岗位本轮最需要验证跨团队推动。

这类内容属于岗位画像或岗位校准，不应写入个人偏好代替岗位规则。

### 3.3 岗位族偏好

适用于一类相近岗位，但不应扩展到全部招聘。例如：

- 对产品岗位，团队结果不能直接证明候选人的个人产品判断；
- 对管理岗位，需要区分本人决策和团队自然增长；
- 对高不确定性岗位，更重视在约束下做取舍的证据。

必须写清岗位族、工作情境和不适用边界。

### 3.4 跨岗位招聘偏好

用户明确希望在多个岗位普遍采用的判断方式，例如：

- 当材料只描述团队成绩时，不把成绩直接归因给候选人；
- 面对强主张但缺少过程证据时，先降低证据置信度，再设计验证；
- AI 与人工结论不一致时，必须保留分歧而不是修改旧建议。

跨岗位偏好仍不能覆盖岗位硬性条件和真实材料。

### 3.5 交互偏好

用户希望 AI 如何协作，例如：

- 先说结论，再说关键依据；
- 批量候选人默认给相对排序；
- 不汇报例行文件操作，只汇报异常或需要决定的事项；
- 给问题时同时给当前倾向和反转条件。

这类偏好影响输出和工作节奏，不应改变候选人能力判断。

### 3.6 不可学习内容

以下内容不能进入有效偏好：

- 用户没有表达、AI 仅从沉默推断的偏好；
- 一次情绪、玩笑或无上下文评价；
- 与工作结果无关的受保护特征；
- 没有证据支持的群体刻板印象；
- 用公司、行业、年龄、地域等代理标签替代个人能力证据；
- 会诱导虚构事实或篡改人工结论的规则。

## 4. 个案决定与稳定偏好的边界

出现以下任一情形时，默认只处理为个案：

- 用户只说了推进、待定或淘汰，没有解释长期原则；
- 结论受当前名额、流程阶段或候选人组合影响；
- 用户是在给一次探索性机会，而不是认可某项能力；
- 反馈针对材料缺失、表述问题或本次面试表现；
- AI 无法区分用户看重的是能力、证据质量还是风险容忍度。

只有用户明确泛化，或多个独立案例呈现同一稳定模式时，才提出长期规则候选。多个案例也只是提出依据，不构成自动确认。

## 5. 反馈理解顺序

按以下顺序理解用户反馈：

1. 用户改变了哪个具体结论；
2. 用户给出的直接理由是什么；
3. 理由指向能力本身、证据强度、风险容忍、岗位条件还是表达方式；
4. 是否存在只对当前候选人有效的背景条件；
5. 是否已有相同或冲突的正式偏好；
6. 最小可复用范围是什么；
7. 哪个反例最可能推翻这次泛化。

不得跳过前四步，直接写一句抽象价值观。

## 6. 规则候选的完整结构

每条规则候选必须包含：

- **规则 ID**：确认后生成唯一 ID；
- **状态**：待确认、已确认、已拒绝、已撤销；
- **类型**：通用招聘判断、岗位族专项或交互偏好；
- **适用范围**：岗位族、职能、阶段、材料类型或交互场景；
- **完整规则**：可直接指导下一次判断的精确表达；
- **决策影响**：改变准入、排序、证据置信度、验证计划或表达方式中的哪一项；
- **证据要求**：什么材料足以触发这条规则；
- **例外**：哪些条件出现时不应机械套用；
- **已知反例**：至少一个能挑战规则的情形；
- **来源**：用户原话、日期和案例路径；
- **不得推出**：这条规则不能被扩展成什么结论；
- **潜在冲突**：与岗位画像或其他偏好的关系；
- **确认信息**：用户确认的日期和原话。

缺少适用范围、证据要求、例外或决策影响的规则不能进入已确认区。

## 7. 从抽象偏好到可观察信号

抽象表达不能直接使用，必须继续追问或改写。

| 模糊表达 | 不足 | 可观察化方向 |
|---|---|---|
| 看重主人翁意识 | 容易变成主观标签 | 是否主动识别问题、做出取舍、推动关键动作并承担结果 |
| 喜欢有业务感的人 | 无法验证 | 是否能说明目标、约束、关键变量和判断依据 |
| 不喜欢只会执行 | 范围过大 | 岗位需要独立判断时，是否有本人提出方案和选择路径的证据 |
| 更看重潜力 | 缺少场景 | 在新问题中学习、修正和迁移方法的具体证据是什么 |
| 在意稳定性 | 易使用代理变量 | 当前岗位所需持续投入条件、候选人真实动机和可验证约束是什么 |

改写后的规则应能改变一个具体动作，而不是只让报告听起来更像用户。

## 8. 适用范围控制

范围从窄到宽依次为：

1. 当前候选人；
2. 当前岗位；
3. 明确岗位族；
4. 明确业务情境；
5. 跨岗位通用；
6. 交互方式。

选择能够解释现有证据的最窄层级。若规则在不同岗位上的价值不同，拆成岗位族规则，不要为了简洁合成通用规则。

范围中可写入：

- 哪类岗位；
- 哪种工作任务；
- 哪个流程阶段；
- 哪类材料或证据；
- 什么前置条件；
- 什么情况下停止使用。

## 9. 反例与过度泛化检查

每次提出规则前至少完成以下检查：

1. 是否存在同样信号但结果相反的候选人；
2. 是否把材料写法误当成实际能力；
3. 是否把一次资源限制下的排序误当成绝对偏好；
4. 是否把“证据不足”误写成“能力不重要”；
5. 是否把某个岗位阶段的需求扩大到长期标准；
6. 是否会误伤经历路径不同但产出等价的人；
7. 是否使用了与工作表现没有直接关系的代理标签；
8. 若规则应用到过去案例，会不会产生用户明显不认可的结果。

如果反例说明规则只在附加条件下成立，就把条件写入范围或例外；如果仍不能消除矛盾，只保留个案结论。

## 10. 证据标准

证据标准应说明“达到什么程度才触发规则”，而不是重复规则本身。

可用证据包括：

- 用户对规则的明确确认；
- 候选人原始材料中的具体职责和行为；
- 面试原话及对应上下文；
- 多个案例中重复出现的明确人工理由；
- 正式岗位画像中的任务和成功条件。

弱证据包括：

- AI 对用户沉默的推断；
- 单个推进或淘汰动作；
- 没有上下文的形容词；
- 文件名、公司名或职位名产生的联想；
- 结果存在但个人贡献不清楚的团队主张。

## 11. 决策影响

每条偏好必须只说明它真正改变的环节：

- **准入**：是否改变必须满足的条件；
- **排序**：相近候选人之间如何取舍；
- **证据置信度**：何时降低或提高某项主张的可信度；
- **面试验证**：下一轮优先追问什么；
- **终面决策**：哪些未验证项可能反转倾向；
- **交互表达**：怎样向用户呈现信息。

如果规则不能改变任何实际动作，就不值得作为正式偏好保存。

## 12. 冲突处理

判断时遵循：

1. 原始事实不能被偏好改写；
2. 公司正式标准优先于个人偏好；
3. 正式岗位画像约束当前岗位；
4. 已确认偏好只在其范围内影响证据和取舍；
5. AI 建议与人工决定分层保存。

偏好与岗位画像冲突时，不静默选择一边。说明冲突的具体内容、会影响哪个候选人或决策，并让用户决定是保留个案、校准岗位还是修改偏好。

两个已确认偏好冲突时，优先使用范围更具体、来源更新且更贴近当前任务的规则；仍无法判断时形成待确认事项。

## 13. 确认、拒绝、修改与撤销

### 提出

待确认提案必须展示完整规则、范围、影响、证据要求和一个关键例外。提案不会影响后续正式判断。

### 确认

只有用户明确同意展示出的完整规则时，才能进入已确认区。用户确认模糊概念，不等于确认 AI 后续补写的详细规则。

### 拒绝

拒绝后不得使用该规则。通常只解决待确认事项；只有保留拒绝原因能避免重复误判时，才写入简短拒绝记录。

### 修改

修改适用范围、规则含义、证据标准或决策影响，都视为新规则提案，不能直接覆盖原文。

### 撤销

撤销需明确记录原规则 ID、撤销范围、原因和日期。撤销不自动回写历史报告或改变已确认候选人结论。

## 14. 多条反馈与重复模式

多个案例出现相似反馈时：

1. 分别保留每个案例的真实原因；
2. 检查是否受到名额、岗位阶段或材料质量影响；
3. 提炼共同的可观察信号；
4. 主动寻找至少一个反例；
5. 形成一条最小范围候选；
6. 仍然请求一次精确确认。

不要用“出现三次所以自动生效”一类机械规则。

## 15. 不可学习内容

遇到以下要求时，拒绝将其保存为有效招聘偏好，并改为与岗位相关的可验证标准：

- 直接基于受保护特征作判断；
- 基于群体刻板印象推断个人能力；
- 用非工作相关个人信息决定排序；
- 要求隐藏证据不足或修改原始材料；
- 要求把 AI 建议伪装成人工结论；
- 要求将一次决定无条件应用于所有岗位。

如果用户表达的真实意图可能合理，例如担心某类岗位的适应风险，应把问题转成任务环境、能力证据和验证条件。

## 16. 已确认偏好的应用审计

在筛选、比较、面试准备或终面简报中应用偏好时，至少留下：

- 偏好 ID；
- 本次适用范围为何满足；
- 触发偏好的具体证据路径；
- 偏好改变了哪项判断或行动；
- 不应用时的基线判断；
- 是否存在例外或冲突；
- 是否需要重新确认适用范围。

不能只在报告中写“根据你的偏好”。用户应能追溯到精确规则。

## 17. 典型示例

### 示例一：个人贡献证据

用户说：“这个项目是团队做的，我没看到他本人做了什么，不要因为结果大就排第一。”

先处理个案：降低该项目对当前排序的证据强度。

可提出的岗位族规则：

> 对需要独立产品判断的岗位，团队结果不能直接证明候选人的个人贡献；至少需要本人识别的问题、关键取舍、推动动作和结果边界。若候选人不是最终负责人，但能证明职责范围内的关键决策和结果，仍可视为有效证据。

不得推出：“来自大团队的人都缺少个人贡献。”

### 示例二：低于 AI 建议仍推进

用户说：“这个人虽然证据不完整，但我愿意给一次面试机会。”

这可能只是探索性个案决定，不能直接提炼为“用户偏爱高风险候选人”。需要确认用户是因为人才稀缺、问题可低成本验证，还是认可某项潜力。

### 示例三：相对排序

用户说：“以后给我候选人时，别只逐个讲，直接告诉我谁先看。”

这是交互偏好：

> 同一岗位有多名候选人时，默认先给相对排序、相邻差异和反转条件，再给逐人摘要。

它不改变候选人的能力判断，只改变汇报顺序。

### 示例四：岗位专属需求

用户说：“这个岗位现在最重要的是能把混乱需求变成清晰方案。”

如果只针对当前岗位，应进入岗位画像或校准建议，而不是写成用户对所有候选人的通用偏好。

## 18. 对话表达

推荐表达顺序：

1. “我理解你这次改变的是……”
2. “这目前更像个案 / 岗位标准 / 可复用偏好候选。”
3. “如果形成规则，完整表述是……”
4. “它只适用于……，会改变……”
5. “例外是……”
6. “是否确认以后按这条完整规则执行？”

确认后说明规则 ID 和未来影响；未确认时不要说“已经记住”。

- 已确认偏好：`00_公司认知/个人招聘判断偏好.md`

- 变更记录：`07_运行记录/系统变更记录.md`
- 应用证据：对应岗位、候选人分析、面试准备或终面简报

偏好主档案是正式来源。索引、对话摘要或日志不能替代它。

## 20. 写入前自检

- [ ] 保留了用户原话和本案结论，没有补写动机；
- [ ] 明确区分个案、岗位标准、岗位族、通用、交互和不可学习内容；
- [ ] 选择了最小适用范围；
- [ ] 规则落到可观察信号，而不是抽象标签；
- [ ] 写明决策影响和证据标准；
- [ ] 至少给出一个例外或反例；
- [ ] 说明了不能进一步推出什么；
- [ ] 检查了与岗位画像及既有偏好的冲突；
- [ ] 未确认规则没有影响正式判断；
- [ ] 确认、修改或撤销都有可追溯记录。
